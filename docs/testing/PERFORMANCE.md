# Performance measurements

Fella has several different costs: preparing a mounted folder, answering a
question through model round trips, the Rust sidecar, and the full Electron
process tree. Keep those measurements separate and record the OS, build type,
workspace, model, and observation interval with each result.

The [16 October 2026 desktop audit](./PERFORMANCE-AUDIT-2026-10-16.md)
records production/development builds, packaged startup, actual navigation,
folder preparation, hosted model turns, process memory, and regression failures
on a pinned WSL2/Linux checkout. It includes the measurement protocol,
reproduction scripts, and the limits of those local observations.

## Available probes

```sh
./scripts/measure.sh
./scripts/measure.sh --bloat
./scripts/measure.sh --build
./scripts/measure.sh --build-cold
./scripts/measure.sh --min
./scripts/check-memory.sh
```

`measure.sh` reports Rust sidecar dependencies, build time, binary size, and
frontend bundle size. It does not launch Electron or measure full-app memory.
The `--bloat` option relinks the optimized Rust binary; cold builds and the
optional probes can take several minutes.

For a Windows Electron process-tree sample, build and run the app with an
isolated profile:

```powershell
pnpm electron:build
.\scripts\measure-windows.ps1 -Seconds 15
```

This sums Electron and Rust child processes for the development executable.
For installed-app comparisons, install and launch the packaged app, hold the
workspace and idle interval constant, and include the entire process tree.
Working set and private bytes are distinct; virtual address space is not
physical memory use.

`check-memory.sh` exercises repeated SQL-backed and pure-Python Wasm runs. It
checks guest memory behavior and, on Linux, process RSS growth; it is not a
full-app leak test.

Capture a report explicitly when needed, for example:

```sh
./scripts/measure.sh | tee /tmp/fella-performance.txt
```

The measurement script no longer appends results to a committed historical
log. Keep raw, machine-specific runs with the benchmark artifacts or local
test records; do not present single-run diagnostics as a product guarantee.

## Recorded ingestion diagnostics

Linux release-mode scale probes recorded in October 2026 include one run that
mounted a mixed workspace with 5,000 small
table sources, 100 text documents, 102 visible unsupported/malformed paths,
and a 10-GiB CSV containing about 275 million rows. The 10-GiB run took about
578 seconds to publish the complete workspace and used about 11.1 GB of SQLite
scratch; the test process reported about 49 MB peak RSS. It loaded the expected
sources and rows. A separate 5,000-small-source run took about 3 seconds.

These are isolated Linux release-build diagnostics, not controlled
comparisons, packaged-app measurements, multi-large-file coverage, or Windows
results. Workspace publication is atomic after preparation, so the UI does not
query partially prepared sources. Incremental refresh and progressively
queryable sources remain open work. See [Roadmap](../product/ROADMAP.md).

## Development and initial-load optimization — 1 November 2026

Scope: development preparation, initial module loading, and unchanged generated
resources. Release optimization and analytical features remain enabled. The
starting commit was `d01b483`; the launcher timeout fix is already included there.
Measurements use Linux/WSL2 x64, Node 24.20.0, Electron 44.5.1, a Ryzen 5600X
host with four visible CPUs, installed dependencies, and disposable app profiles.
Windows execution and build-memory peaks were not measured here.

Criteria set before candidate checks: no production frontend/release-engine
build in everyday `electron:dev`; exactly one contract preparation; explicitly
launch the new development binary; preserve generated bytes and invalidate the
cache for changed inputs/outputs; retain immediate saved answers, SQL, Report
charts, Settings, Search and review interactions without unexpected reloads.
Record startup, idle memory, preparation costs and unsuccessful experiments
separately. Do not treat lower development preparation cost as lower app RAM.

| Measurement | Before | After |
| --- | ---: | ---: |
| Warm preparation before Vite | 24.90 s (`electron:build`) | 0.94 s (`electron:prepare:dev`) |
| Largest-process peak RSS during that preparation | 1,868,360 KiB | 135,000 KiB |
| Full catalog generation / verified cache hit | 1.528 s | 0.046 s |
| Initial static JS graph, raw bytes | 1,201,938 | 878,249 |
| Initial static JS graph, gzip comparison bytes | 351,934 | 270,027 |
| Shared Wasm bytes | 1,202,192 | 1,202,192 |
| Composer + engine ping, median of three isolated production-asset starts | 624.3 ms | 586.5 ms |
| Total idle process-tree PSS, median of those starts | 387.9 MiB | 390.7 MiB |

These are small local samples, not universal speed guarantees. The initial JS
figures traverse static manifest imports for app/start/layout/page; deferred
chunks and the error route are excluded. This is an asset graph measurement,
not observed network traffic or a claim that the complete application shrank.
The Wasm validator and primary answer renderer remain ready synchronously.
Secondary Settings, Search, report/Investigation implementation, and revision
review modules load only when used. The local Electron protocol serves raw
assets; gzip sizes are comparison figures rather than network transfer costs.

The warm preparation comparison deliberately removes unnecessary production
work rather than changing release settings. `/usr/bin/time` reports the largest
process RSS, **not a sampled aggregate build-process memory peak**. The first
build after reducing development debug info took 92.14 s including a target-lock
wait and dependency recompilation; that one-time cache transition is not the
warm result. A subsequent same-content timestamp-triggered own-crate rebuild
and preparation took 5.53 s; real source edits can invalidate more work. The
native release build remains fully optimized and development binaries are
larger and unoptimized Rust, so use release builds for analytical performance
comparisons. Bundled SQLite remains optimized in development.

An initial post-change startup sample taken alongside other Electron/build work
showed a 752.8 ms median and 301.5 MiB PSS. The concurrent instances redistribute
shared-page PSS and invalidate a memory-savings interpretation. The isolated
repeat above shows **no meaningful idle-memory reduction**. Preserve both runs;
do not claim the confounded memory drop as an optimization.

Validation and limitations:

- Full generator output is byte-identical under `--force`; cache hits preserve
  output mtimes. Corrupted catalog and missing compact contract both regenerated
  the exact expected bytes. Local cache metadata is ignored and content-hashed.
- Actual `pnpm electron:dev` logs select the debug engine, prepare once, serve
  Vite, and reach interactive state. The established Playwright Electron smoke
  additionally verified engine SQL `42`, automatic sample Report restoration,
  three nonzero canvases, Settings and the real Search button/dialog. No Vite,
  renderer or no-workspace errors occurred in that smoke.
- The custom CDP launcher harness had early/empty-target attachment failures.
  One isolated run reached SQL, all Report charts and Settings, then failed
  because CDP keyboard input does not activate Electron's native menu shortcut.
  These failures remain recorded; the distinct direct-Electron check used the
  actual Search button instead. Running generation/check tools concurrently
  with dev UI checks also triggered expected SvelteKit development reloads;
  avoid that confound when grading app-generated reload behavior.
- Focused JSON-render, exact export and Report-design regressions pass, as do
  all 28 frozen native/Wasm acceptance cases. Frontend checking reports zero
  errors/warnings and the production build succeeds. No model prompt, evidence
  contract, or frozen benchmark expectation changed in this optimization.
- Review harness v1.0 failed a module-request assertion that also counted the
  Vite CSS proxy. Under the previously approved bundled-asset distinction,
  v1.1 excludes style requests while retaining the one-component-module
  assertion. The user then approved scoping the primary-answer locator to
  the answer surface rather than counting the comparison preview; v1.2 reruns
  the same behavioral assertions under that explicit correction. Cached primary display, real comparison, close/reopen, stale
  workspace/unmount/close guards, import failure, and uncached artifact-revision
  assignment 2→3 pass. The uncached case exposed a real cancellation bug in the
  new guard: artifact resolution assigns its own revision, so revision changes
  no longer cancel that user's pending review. Its input identity and workspace
  guards remain. Old failing logs are preserved under `/tmp/fella-answer-review-*`.
- A no-`regex/perf` experiment failed its predetermined 20% size-reduction gate:
  byte-identical Wasm, 28/28 parity, 6.023 ms warm-batch median versus 5.10 ms
  baseline (within its 2x timing limit). The feature edit was reverted. There
  is no claimed validator size win.

Raw local evidence is under `/tmp/fella-build-performance-before.log`,
`/tmp/fella-dev-preparation-{first,reduced-debug,warm,edit}.log`,
`/tmp/fella-performance-{before,after,after-isolated}/`,
`/tmp/fella-performance-direct-electron.log`, and
`/tmp/fella-regex-perf-experiment-1793550591690/`. The latter includes restored
artifact hashes and the failed experiment. Reproduce the preparation probe with
`pnpm electron:prepare:dev`, and production-asset startup sampling with
`node scripts/profile-desktop.mjs --startup-only --startup-runs 3 --output <directory>`.

# Fella as the data analyst's harness

**Status:** Product investigation, 2026-10-10. This records a product thesis
and a static audit of the current desktop app; it is not a release commitment.

## Product thesis

Fella should embody the way a data analyst works, not merely answer questions
about files. Its core job is to help carry an ambiguous problem through
filesystem discovery, decomposition, evidence-backed computation, quality
checks, visualization, and a result someone else can use.

The analyst remains responsible for the business question, material
definitions, and judgment about whether the answer is fit to share. Fella
should make the work easier to perform and easier to inspect—not imply that a
successful query or a model-generated answer is automatically correct.

This gives Fella a focused story without requiring a CLI, FellaDB, or a
separate Projects/wiki/dashboard layer:

> **Fella is an AI analytics harness for analysts working with files. It helps
> take a question from the first look at a folder to an answer whose evidence,
> checks, and visualization can be inspected and handed on.**

“Handed on” is a product direction, not a claim that the app currently creates
a complete stakeholder deliverable. A more accurate description of today's
experience is: **ask a question of a folder, then inspect how Fella analyzed
it.**

## The analyst's workflow mapped to Fella

The workflow below reflects the user's own practice. It can take a week or a
month; it is not a required sequence of model tool calls. The harness should
support the lifecycle while allowing the analyst to choose the next useful
step.

| Analyst work | What Fella supports today | Finding / remaining gap |
| --- | --- | --- |
| 1. Get the problem | Ask accepts open-ended questions. The app can request a typed clarification when a material interpretation remains unresolved. | The problem, decision to inform, intended audience, and acceptance criteria are not a durable brief. They live in conversation prose. |
| 2. Find out what data is available | A mounted folder is cataloged. Sources shows readable and skipped files, table dimensions, columns/types, some distinct/common values, and bounded previews. The composer has **Check data**, explicitly described as starting with the files and showing checks. | This is a real strength. The inventory is still a separate view or an analysis turn, rather than a persistent “what we know about this dataset” section of an investigation. The current scope is the selected workspace, not the whole disk. |
| 3. Decompose the big question | The engine instructs the model to inspect profiles and observed values, decompose multi-part questions, refine scope/fields/filters/grain/joins, and use an analysis contract for material semantic decisions. | Decomposition and the working interpretation are mostly model/runtime behavior. The user does not get a durable, editable list of subquestions and assumptions before or during execution. |
| 4. Answer the smaller questions | Follow-ups stay in a conversation, can use recent context, and can retrieve earlier execution evidence when it belongs to that conversation and the current workspace revision. Clarification resumes the same analysis thread. | There is no first-class subquestion tree, dependency/progress state, or investigation-level record of what has been answered and what remains open. A long thread is not equivalent to a managed investigation. |
| 5. Build the query | Fella chooses among SQL, sandboxed Python, document tools, and other enabled analysis routes. Analysis Details can reveal generated SQL, Python/calculation inputs, arguments, and results. | The query/calculation is primarily generated by the model and exposed after the run. It is not a live, step-by-step working surface that an analyst can revise, annotate, or keep as an explicit investigation step. |
| 6. Run the query | The local Rust engine provides scoped, read-only data access and bounded execution. Source files are not edited by analysis. | This is a solid harness boundary. It gives Fella an execution substrate, but the active run surface could communicate the selected scope and intermediate outputs more clearly. |
| 7. QA the query and result | Deterministic verification checks replayable computations and selected invariants; actionable findings can trigger targeted repair. Evidence Details shows sources, queries, returned rows, warnings, and check results. | These checks catch important execution/evidence problems, but cannot prove the business interpretation is right. There is no explicit coverage review showing each part of the original brief, its supporting evidence, and what was not tested. The analyst still has to decide whether the checks cover the bases. |
| 8. Build the visualization | Structured charts are part of the answer, include exact values/details, and can be copied or downloaded as PNG; chart data can be copied or downloaded as CSV. | The export path is useful and already supports reuse. The chart is still an answer artifact, not a deliberately composed visual with audience framing, annotation, and its supporting method packaged alongside it. |
| 9. Hand it to the requester | The analyst can share answer text and chart/data exports; evidence remains attached to the conversation. | There is no one-piece handoff that brings together the question, scope, definitions, method/query, QA, caveats, findings, and visualization. Preparing that deliverable remains manual. |
| Work over days or weeks | Conversations persist, analytical turns have separate local records, the workspace can carry a user-authored `fella.md` guide, and prior evidence is guarded by workspace revision. | There is no durable investigation/case object that tracks the problem, scope changes, decisions, subquestions, completed checks, open work, and handoff readiness across many sessions. Revision-aware recomputation is valuable, but a changed workspace can also mean old evidence is no longer reusable. |

## What the app already gets right

Fella is not starting from a blank slate or just wrapping a chat model around
CSV files:

- **It is data-first.** It catalogs an explicitly selected folder, surfaces
  useful source and field information, accounts for skipped files, and lets
  the user start with **Check data** rather than inventing a question too
  early.
- **Its analysis loop reflects analyst habits.** The engine prompt treats an
  inventory as reconnaissance, directs the model to inspect before computing,
  decompose multi-part questions, refine the grain and population, and revisit
  inspection when a result is empty or inconsistent.
- **It can resolve ambiguity interactively.** Material choices can be raised
  as a typed clarification and continued in the same conversation, rather
  than hidden in a prose question at the end.
- **Execution has meaningful boundaries.** SQL is read-only; Python runs in a
  bounded sandbox; the model chooses tools but the runtime owns scope and
  execution controls.
- **Evidence is inspectable after a run.** The answer can retain source
  references, queries/calculations, result rows, checks, and chart data.
  This makes a result more auditable than an answer with citations alone.
- **Visual outputs can leave the app.** Copy/download support for chart images
  and data is already a practical handoff primitive.

These capabilities make Fella a credible filesystem analytics harness. They
should be the foundation of the story, not obscured by a generic “AI analytics
app” description.

## The main product gap: hidden method, turn-shaped experience

The strongest gap is not that the runtime lacks analyst behavior. It is that
the interaction makes the work feel like **one prompt → one answer**. During a
run, the timeline offers a compact activity summary; after completion, that
timeline is hidden when an answer exists and the detailed trace is available
under a collapsed evidence disclosure. That is useful auditability, but it
does not yet feel like steering an investigation as it develops.

For an analyst, control means being able to tell and influence:

- what question Fella believes it is answering;
- which files, tables, and fields it has chosen;
- how the large question has been broken down;
- which assumptions or definitions could change a result;
- what query/calculation ran and what it returned;
- which parts of the brief have been answered or checked;
- what remains uncertain, unsupported, or ready to hand off.

This points toward a persistent **investigation** inside the existing desktop
analytics experience—not necessarily a full notebook, generic project system,
or a fixed pipeline. A lightweight investigation could start by making the
question, selected workspace revision, evolving subquestions, assumptions,
evidence, checks, visualizations, and open items visible together. The user
should be able to correct a material interpretation and continue without
having to reconstruct the work from a long transcript.

## Notebook-style Investigation: design line items

The notebook is a presentation of model-directed analysis, not a workflow
template that determines which actions the model must take. These line items
describe the interaction to explore; they are not a commitment to reproduce a
Jupyter or Hex notebook.

1. **Let the model choose the work.** The model selects the useful analytical
   actions for the question and available data. It may add, omit, reorder, or
   revisit steps; do not require every Investigation to follow the same stages.
2. **Show the work in the order it happened.** Present meaningful analysis
   actions and their outputs as an ordered, readable record. Distinguish work
   already performed from a possible next action; do not display a planned step
   as completed evidence.
3. **Do not make steps a completion gate.** An unanswered, skipped, unsupported,
   or inconclusive step does not by itself fail the run or suppress its answer.
   Return the best-supported answer available, while clearly stating material
   assumptions, uncertainty, and evidence gaps. Never imply certainty the data
   does not support.
4. **Give each step a concise purpose and result.** Where applicable, show what
   the model attempted, the relevant input or source scope, the result it
   observed or computed, and its interpretation. Keep these distinct rather
   than blending them into one narrative claim.
5. **Keep evidence beside the conclusion it supports.** Show useful tables,
   values, and visualizations in context, with a direct path to the source,
   query/calculation, execution record, and source revision behind them.
6. **Represent checks accurately.** Show only checks that actually ran and
   explain what each establishes. A skipped or unavailable check is a disclosed
   limitation, not a failed checklist item; a passing execution check must not
   be presented as proof that the business interpretation is correct.
7. **Support steering without requiring step-by-step operation.** Let the
   analyst correct a material assumption, ask a follow-up, or request another
   analysis at any point. Routine steps should not require approval one by one
   or an up-front commitment to a fixed plan.
8. **Preserve iteration and provenance.** If the model revises or reruns work,
   retain the relationship to prior steps and results, identify what changed,
   and mark dependent results that need refreshing. Do not silently rewrite the
   historical record.
9. **Use progressive disclosure.** Keep the default step readable for a
   non-specialist; expose query logic, parameters, detailed rows, and technical
   checks when the user asks to inspect them. A small question should not turn
   into a verbose procedural report.
10. **Make the answer easy to recover.** Keep the current answer and key
    findings readily visible, with links into the ordered work record for
    evidence and method. The user should not have to read every step to find
    the result or reopen the original chat to understand it.
11. **Show useful explanations, not hidden reasoning.** Summarize actions,
    evidence, decisions, and concise rationale. Do not expose raw internal
    reasoning or invent a tidy step-by-step explanation after the analysis.

## Priority questions for product design

1. **Continuity:** How does an analyst return after a day or a week and see the
   question, scope, progress, prior decisions, and next useful action at a
   glance?
2. **Steerability:** Which intermediate choices need to be directly editable
   or confirmable, and which should remain automatic unless the evidence
   signals a material ambiguity?
3. **Coverage:** How should Fella show that each requested part was answered,
   what evidence supports it, which QA checks ran, and what could not be
   established?
4. **Handoff:** What is the smallest useful shareable analysis brief that
   preserves the result, visualization, method, scope, definitions, checks,
   and caveats without making every chat answer into a report?
5. **Trust language:** How can the UI distinguish deterministic execution
   checks from analyst-owned semantic/business validation, so “passed” never
   implies more than the system established?

These are product-design questions, not accepted implementation tasks or a
release schedule. They complement the notebook-inspired transparency direction
in [Stack vision](STACK-VISION.md) while keeping the focus on the analyst's
filesystem workflow.

## Evidence and audit limits

This investigation reviewed the repository's product and architecture docs,
the desktop conversation/composer/timeline/evidence/chart/source components,
the Rust analysis prompt, semantic workspace model and verifier, persistence,
and the documented evaluation journeys. It was a static code-and-document
audit: no live model session, user study, or test suite was run for this
document.

Implementation evidence includes [SourcesView](../src/lib/components/SourcesView.svelte)
and [SourcePreview](../src/lib/components/SourcePreview.svelte) for discovery;
[Composer](../src/lib/components/Composer.svelte) for Ask/Check data and context
selection; [the analysis loop](../backend/src/engine/agent.rs) and
[workspace model](../backend/src/engine/workspace_model.rs) for interpretation
and decomposition guidance; [RunTimeline](../src/lib/components/RunTimeline.svelte),
[EvidenceBlock](../src/lib/components/EvidenceBlock.svelte), and
[analysis persistence](../backend/src/engine/analysis_store.rs) for visibility
and continuity; [verification](../backend/src/engine/analytics/verify.rs) for
QA boundaries; and [Chart](../src/lib/components/Chart.svelte) for visual
exports.

The documented desktop journey already exercises source coverage, aggregates,
cross-file reconciliation, data-integrity questions, charts, follow-ups,
forecast/scenario questions, missing-data limits, and interactive
clarification. That journey explicitly checks workflow, **not answer
correctness**; analytical quality is evaluated separately in FQA-Bench, whose
coverage and results should be treated according to its documented task sets
and limitations. Neither is yet a complete week-long analyst-to-stakeholder
handoff evaluation.

for runtime boundaries, [Roadmap](ROADMAP.md) for current priorities, and
[desktop journey coverage](testing/E2E-JOURNEYS.md) for the tested workflow

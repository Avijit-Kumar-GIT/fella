The harness is the control layer around the selected model. It assembles context, exposes approved tools, validates and executes tool calls, records evidence, and finishes the answer.

## Context and scope

For a workspace conversation, the request can include the active folder catalog, relevant source profiles, the immediate user message, recent conversation context, workspace context, and—when the conversation belongs to an Investigation—the selected Question, source scope, and saved definitions or assumptions.

The harness records the workspace revision and Investigation context used by each run. Later edits do not rewrite the saved run.

Without a mounted workspace, data-analysis tools are unavailable. The model can still answer general questions, but those answers have no workspace evidence.

## Tool loop

1. The selected model returns text or a request to use one or more registered tools.
2. The harness validates tool names and arguments, then sends approved calls to the Rust engine.
3. The engine returns bounded results or an explicit error.
4. The harness records the result as evidence and supplies it to the next model turn.
5. When the model finishes, deterministic verification checks the answer against available evidence and execution records.

The model can inspect, calculate, revise its interpretation, and combine tools as needed. SQL and sandboxed Python are both available; document search and reading are separate paths. The harness is model-directed but the engine enforces execution scope.

## Presentation composition

When accepted analysis results support a useful structured view, the model composes a JSON-render document using the registered component catalog. It can choose a prose, metric, table, chart, or mixed layout that fits the question. It is not required to produce the same visualization for every result.

Analytical values reference saved result IDs and fields. The validator rejects unknown components, invalid props, missing results, and unsupported bindings. The renderer does not execute model-authored code and cannot independently access workspace files. Presentation failure leaves the canonical answer and analysis evidence available.

Saved presentation snapshots allow the interface to restore an answer without calling the model or recomputing the analysis merely to reopen the conversation.

## Guidance and enforcement

| Layer | Example | Enforced by |
| --- | --- | --- |
| Prompt guidance | Inspect relevant files and explain uncertainty | Model instructions; guidance can be misunderstood |
| Tool access | Call only registered tools | Rust dispatcher and schemas |
| Data boundary | Read cataloged sources and run bounded queries | Workspace catalog and analytics engine |
| Python boundary | Run in an embedded WASM guest without filesystem, network, or subprocess access | Wasmi host interface and resource limits |
| Verification | Check replay, grounding, and known result risks | Deterministic verifier |
| Presentation | Render a validated tree bound to supplied results | Presentation schema, result binder, and Svelte component registry |

## Limits

- The model may misunderstand a question or choose a semantically wrong query.
- Tool success is not proof that a query answered the intended question.
- Verification can identify concrete inconsistencies but cannot guarantee correctness.
- JSON-render validates what is shown; it does not validate the meaning of the model’s prose by itself.
- No model output can add a shell, filesystem write operation, web tool, or connector.

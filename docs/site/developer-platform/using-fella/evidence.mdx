The **How this was analyzed** disclosure under a Chat answer is collapsed by default. Open it when you want to understand what the run actually did. It records observable tool activity, not hidden model reasoning.

## What a run records

| Record | What it tells you |
| --- | --- |
| Workspace revision | Which catalog snapshot was mounted when the run began. |
| Source scope | Which files and tables were used or excluded for that run. |
| Tool trace | The inspection, SQL, document reads, Python calculations, chart work, errors, and timings. |
| Result | The values returned by the engine, including whether a result was truncated. |
| Verification | Which consistency and grounding checks passed, warned, or affected an output. |
| Presentation | The structured view and the saved result bindings used to render it, when a view was composed. |

The run is a historical record. Editing the current Investigation’s Question, selected files, or definitions does not rewrite a completed run.

## Inspect an answer

1. Confirm that the run used the expected source files and tables.
2. Check query filters, joins, date boundaries, denominators, and units.
3. Compare the returned result with the answer’s claims.
4. Review warnings and any excluded result or withheld presentation.
5. If the workspace has changed, inspect the source revision before reusing the answer.

In Notebook, the **Analysis** section organizes saved runs and their details across an Investigation. **Results** shows current Question coverage and saved Findings. It is fine to inspect a run without opening every detail; the deeper trace stays available when you need it.

## What verification means

Verification checks specific properties of recorded work, such as SQL replay, numeric grounding, known query risks, result consistency, and whether a chart agrees with its bound result. A warning identifies something to review; it is not automatically a judgment that the whole answer is wrong.

A green status is not proof that the model chose the right business definition or population. A valid calculation can still answer the wrong interpretation. Inspect the source data and method for consequential decisions.

## Structured answers and fallback

JSON-render presentations use registered components and saved result IDs and fields. The client validates the component structure and analytical bindings before rendering. Presentation controls can change only the displayed state or request an explicit user-started follow-up; they cannot change source files or run hidden queries.

If a structured view cannot be composed or displayed, Fella keeps the canonical answer and analysis details available as text. Reopening a saved presentation uses its stored snapshot and does not require a fresh analysis run.

## Preserve and compare

Save a useful output to Reports. Its revision stays linked to the run and exact results. When you revise it, the analytical diff describes changes in meaning, inputs, method, results, and known report impact. Numeric deltas are withheld when the outputs cannot be safely aligned.
